# pharma-ltm-assistant

Долгосрочная память (LTM) AI-ассистента аптеки. Ассистент общается с покупателем и помнит, что тот о себе рассказывал: какие препараты принимает, на что аллергия, есть ли хронические заболевания, беременность, для кого покупает.

Архитектура повторяет подход из статьи [«Долгосрочная память для медицинского AI-ассистента: почему мы не отдали управление памятью LLM»](https://habr.com/ru/articles/1090888/) и переносит его на аптечный домен.

## Принцип

**LLM понимает смысл, состоянием памяти управляет код.** Модель классифицирует запрос и извлекает из диалога структурированные события. Всё остальное детерминировано: валидация, нормализация названий, ID, время, тип изменения, итоговый статус факта и выборка контекста.

```
write-path (фон)
  диалог ─► [LLM] разделы ─► [LLM] extractor ─► Pydantic-валидация ─► нормализация ─► state machine ─► SQLite
                                                   невалидное → rejections        ТН → МНН            facts + events

read-path (синхронно)
  запрос ─► [LLM] тип запроса ─► набор разделов ─► фильтр статусов и сроков ─► контекст с пометкой источника
                                                                              + список «уточнить у покупателя»
```

## LLM-шаги

Модель — [Qwen3-4B-Instruct-2507](https://huggingface.co/Qwen/Qwen3-4B-Instruct-2507), 4-bit NF4 в Colab T4, жадное декодирование.

| Шаг | Что делает модель | Что делает код |
|---|---|---|
| Классификатор разделов | какие разделы затронуты в фрагменте диалога | отбрасывает неизвестные разделы; при сбое запускает extractor по всем разделам; **страховка**: препарат из справочника в диалоге добавляет раздел `medications` |
| Extractor | события по **одному** разделу; в промпте правила и примеры только этого раздела | повтор при битом JSON и при невалидных событиях, отсечение фактов чужого раздела, поэлементная валидация, проверка по справочнику |
| Классификатор запроса | тип запроса и о ком он | отбрасывает неизвестные типы; при сбое — правила |
| Ответ | ответ покупателю | контекст с пометкой источника, блок СПРАВОЧНИК по упомянутым препаратам, список «уточнить» |

Write-path запускается после фрагмента диалога (`ChatSession.close()`) и видит реплики покупателя и только вопросы ассистента; read-path — на каждое сообщение. Ответы модели, которые не удалось разобрать, пишутся в `rejections` вместе с сырым текстом.

Бэкенды с одним интерфейсом: `QwenTransformersLLM` (Colab), `OpenAICompatLLM` (vLLM, Ollama, LM Studio), `CachedLLM` (кэш ответов на диск), `ScriptedLLM` (тесты).

### Dev-набор

`data/dev_dialogs.jsonl` — 17 диалогов (d17 добавлен после прогона 2 по сбою живого диалога): каждый раздел, отрицания, «не знаю», покупки для ребёнка и мамы, препарат только в вопросе, изменения уже сохранённых фактов. Для каждого — эталонный ответ extractor-а и ожидаемое итоговое состояние памяти. `data/dev_queries.jsonl` — 20 запросов с типами и субъектом.

Сравнивается итоговое состояние памяти (ключ после нормализации и статус после state machine), а не дословный JSON. Тест прогоняет эталонные ответы через весь пайплайн и требует 100% совпадения: так проверяются сами эталоны.

**Прогон 1 → что исправлено.** Классификатор разделов не ошибся ни разу; все потери — в extractor.

| Ошибка модели | Пример | Исправление |
|---|---|---|
| Пропущен второй препарат при замене | «Энап больше не пью, врач перевёл на Лозап» → только Энап | правило и пример «заменил X на Y» в промпте |
| Не извлечено исправление сказанного | «ошиблась — аллергии на него нет» → пусто | общее правило про исправления и местоимения, пример |
| «Не знаю» про аллергию записано в хронические | раздел `chronic_conditions`, цитата про аллергию | правило раздела, пример-«ловушка»; пример `dont_know` для аллергий |
| Препарат записан как диагноз | «Варфарин» в `reported_diagnoses` | **код:** название из справочника препаратов в разделе болезней или симптомов отклоняется |
| Пропущен `evidence`, мусор в `section_statuses` | `{"section_statuses": ["active"]}` для симптомов | **код:** один повтор со списком ошибок валидации; разделам без «нет ≠ нет данных» `section_statuses` больше не показывается |
| В живом диалоге факты первой реплики не сохранились | длинные ответы ассистента в диалоге | **код:** write-path видит реплики покупателя и только вопросы ассистента |
| Ответ выдумал, что за препарат | «Лозап (лозаприл, ингибитор АКК)», «50 мг — опечатка» | **код:** блок СПРАВОЧНИК с МНН и группой для упомянутых препаратов; правило «не оспаривать назначения врача» |
| Лишний тип запроса | «Маме можно Найз…» → + `pregnancy_lactation` | тип только при явном упоминании беременности или ГВ; сообщение без вопроса → `general` |

**Прогон 2 → что изменилось.** Исправлены d06 (замена препарата), d09 («не знаю» про аллергию), d11 (статусы разделов), d12 (исправление сказанного); регрессий нет. Проверка по справочнику сработала: «Варфарин» в диагнозах отклонён кодом. В живом диалоге ответы стали короткими, Лозап назван лозартаном из справочника, факты первой реплики сохранились.

| Что осталось | Последствие | Решение |
|---|---|---|
| Классификатор пропустил `medications` в живом диалоге («пью Лозап 50» рядом с гипертонией и аллергией) | препарат не попал в память, во второй сессии ассистент снова спрашивает о лекарствах | **код:** страховка маршрутизации по справочнику; диалог добавлен в dev-набор как d17 |
| Ответ назвал неверную суточную дозу парацетамола и посоветовал «избегать нитроглицерина» | модель 4B выдумывает дозировки | **промпт:** дозы не называть, отсылать к инструкции; дозировки из справочника — этап 4 |
| d13: «кашель уже прошёл» не извлечён | кашель остаётся актуальным, пока не истечёт срок жалобы (14 дней) | оставлено: кандидат для сравнения с 7–8B на этапе 3 |
| d10: Монурал «назначил — вот пришла за ним» → `active` вместо `prescribed` | оба статуса актуальные, препарат попадает в контекст в любом случае | оставлено: пограничный случай |
| Сообщение без вопроса классифицировано как `therapy_history` | ассистент дал непрошеный совет вместо «чем помочь?» | оставлено |

Дальше подгонять промпты под 17 диалогов — значит переобучаться на dev-наборе: живой диалог нашёл ошибку, которой в нём не было. Поэтому следующий шаг — отдельный golden set (этап 3).

Новые примеры в промптах не повторяют dev-набор, чтобы метрики не завышались. Полные отчёты прогонов с сырыми ответами модели лежат в `reports/`.

## Оценка по слоям (этап 3)

### Golden set

`data/golden/` — отложенная выборка: по ней промпты **не настраиваются** (для этого служит dev-набор). Тест проверяет, что в ней нет почти-дублей реплик из dev-набора и из примеров в промптах; три найденных при сборке дубля перефразированы. Разметку собирает `scripts/build_golden.py`; тест проверяет, что скрипт воспроизводит файлы данных.

| | Количество |
|---|---|
| Сценариев | 97: 85 одиночных сессий и 12 многосессионных (паузы до 240 дней) |
| Сессий | 106 |
| Проб контекста после сессий | 20, из них с проверками ответа — 11 (12 проверок) |
| Запросов для классификатора | 40 |

Покрытие: все 8 разделов; лекарства в разных статусах, дозировки, опечатки, падежи, препараты вне справочника; отрицания и исправления сказанного; «нет» и «не знаю» на уровне раздела; ответы «да», «нет», «семь» на вопросы ассистента; покупки для детей, родителей и супругов, несколько субъектов в одной реплике; ловушки: препарат только в вопросе, препарат назвал ассистент, гипотетический вопрос, вопрос за третье лицо. Многосессионные сценарии проверяют замену препарата, историю терапии, роды после беременности, аллергию после «аллергий нет», исправление, забывание жалобы через 14 дней, противоречие, изоляцию субъектов, повторное начало приёма.

Разметка записана дважды: ответ extractor-а и ожидаемый снимок памяти после каждой сессии. Эталонный бэкенд прогоняет первое через весь пайплайн и должен получить второе на всех слоях ровно на 100%, иначе ошибка в разметке или в коде. Golden set составлен с помощью Claude; согласованность разметки с кодом проверяется тестом, смысл эталонов стоит выборочно проверить вручную.

### Что измеряется

| Слой | Метрики |
|---|---|
| Классификатор разделов | P/R/F1 по разделам; сколько разделов добавила страховка и сколько из них нужных |
| Extractor | события: P/R/F1 по ключу (раздел, субъект, название после нормализации); точность полей (полярность, статус, тип реакции, дозировка и т. д.); статусы разделов; доля цитат `evidence`, найденных в диалоге; повторы и отклонения кодом |
| Память | итоговые факты и статусы разделов после state machine: P/R/F1, атрибуты, сценарии без ошибок |
| Retrieval | нужные факты в контексте, лишних нет, верные «уточнить»; дважды: с эталонным типом запроса (чистая логика выборки) и с LLM-классификатором (E2E) |
| E2E | факт из прошлой сессии учтён в ответе; доза не названа. Эвристики по тексту ответа |
| Классификатор запроса | точное совпадение типов против baseline на правилах |

Каждая ошибка памяти приписывается этапу пайплайна: классификатор, пропуск extractor-а, статус или полярность, субъект, нормализация названия, валидация, каскад из прошлой сессии. Это и есть «проверяем всю цепочку» из статьи: видно не только, что ответ неверный, но и где именно.

### Как запускается

Классификация и extraction не зависят от состояния памяти, поэтому ответы модели генерируются заранее пакетами (`warm_cache`): сначала классификаторы, затем extractor по разделам, затем повторы по ошибкам валидации. Сообщения строятся теми же функциями, что и в пайплайне, поэтому последовательный прогон берёт всё из кэша. Тест проверяет, что после прогрева прогон не делает ни одного нового вызова. Кэш хранится на Google Drive: оборванный сеанс продолжается с того же места.

## Разделы памяти

| Раздел | «Нет» ≠ «нет данных» | Срок актуальности |
|---|---|---|
| Лекарства | да | бессрочно |
| Аллергии и непереносимость | да | бессрочно |
| Хронические заболевания | да | бессрочно |
| Беременность и лактация | да | 280 / 365 дней, потом переспросить |
| Возраст, пол, вес | — | вес 180 дней (дети растут) |
| Образ жизни (курение, алкоголь, вождение) | — | 365 дней, потом переспросить |
| Жалобы и симптомы | — | 14 дней, потом не попадает в контекст |
| Диагнозы со слов покупателя | — | 30 дней, потом не попадает в контекст |

Факты хранятся отдельно для каждого субъекта: сам покупатель, ребёнок, мама и т. д.

## Переходы состояния

Тип изменения определяет код по переходу статуса и сравнению атрибутов:

| Было → стало | Тип |
|---|---|
| — → актуальный | `first_mention` |
| — → отсутствует («аллергии на X нет») | `denial_recorded` |
| актуальный → тот же, без изменений | `confirmation` |
| актуальный → актуальный с другими атрибутами или статусом | `update` |
| актуальный → неактуальный («больше не пью») | `deactivation` |
| актуальный → отсутствует («оказалось, аллергии нет») | `negation` |
| неактуальный → актуальный | `reactivation` |

Отдельно для разделов:

* «Аллергий нет» → `confirmed_absent`; «не знаю» → `dont_know`; отсутствие записи → «не обсуждали».
* Новая аллергия перекрывает прежнее «аллергий нет».
* «Аллергий нет», когда в памяти есть актуальная аллергия, → `conflict`. Факт не удаляется, раздел помечается для уточнения.

## Что добавлено к подходу статьи

* **Нормализация кодом.** «Энап 5 мг» и «эналаприл» — один факт. Дозировку из названия достаёт код. Опечатки распознаются нечётким поиском, неоднозначные совпадения не угадываются.
* **Забывание по типу факта.** Устаревшая жалоба уходит из контекста, давнее «беременна» помечается для уточнения, аллергия не устаревает. В статье механизма забывания пока нет.
* **Конфликт как отдельное состояние** вместо молчаливой перезаписи.
* **Субъекты.** Покупатель часто берёт лекарства для ребёнка или родителей.
* **Документированный источник.** История покупок по карте лояльности идёт отдельным блоком с пометкой происхождения. Resolver-а нет: при расхождении основная модель уточняет.

## Структура

```

  sections.py        разделы и их политики: статусы, «нет» ≠ «нет данных», сроки

  lexicon.py         сопоставление со справочником: точное, по префиксу, нечёткое
  reference_data.py  seed-справочники: препараты (ТН → МНН), аллергены, заболевания, симптомы
  normalize.py       нормализация по разделам и субъектам
  store.py           SQLite: facts (состояние), events (история), section_states, rejections
  memory.py          write-path: state machine
  retrieval.py       read-path: разделы, статусы, сроки, «уточнить», рендер контекста
  query_rules.py     baseline-классификатор запроса на правилах
  llm.py             бэкенды моделей, кэш, устойчивый разбор JSON
  prompts.py         промпты: классификатор разделов, extractor по разделу, классификатор запроса, ответ
  pipeline.py        write-path, read-path, ассистент, сессия чата
  devcheck.py        проверка на dev-наборе, эталонный бэкенд
  evaluation.py      оценка по слоям на golden set, разбор ошибок по этапам, сравнение моделей
scripts/
  build_golden.py    сборка golden set
data/
  dev_*.jsonl        dev-набор (для настройки промптов)
  golden/            golden set (отложенная выборка)
reports/             отчёты прогонов с сырыми ответами модели
tests/               тесты по слоям: схемы, нормализация, переходы, выборка, промпты, пайплайн, golden set, оценка
notebooks/
  01_core_demo.ipynb    ядро на сквозном сценарии
  02_llm_pipeline.ipynb LLM-шаги на Qwen
  03_evaluation.ipynb   оценка по слоям, сравнение моделей
```
